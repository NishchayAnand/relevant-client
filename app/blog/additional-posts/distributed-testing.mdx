Quality assurance (QA) of systems distributed across multiple servers or regions can not 
be achieved using localized and single-node testing processes.

Software is usually verified at three levels. The difference is how much of the real system is running during the test.

---

### Unit Testing

Test individual units of code independently to verify that they behave as expected.

**The AAA pattern**: A good unit test generally follows three stages:

1. **Arrange**: Prepare the test environment.
2. **Act**: Execute the method being tested.
3. **Assert**: Verify the actual result against the expected result.

#### How to write unit tests?

JUnit provides the testing framework. Mockito allows us to create mock dependencies.

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    private UserRepository userRepository;

    @InjectMocks
    private UserService userService;

    @Test
    void shouldReturnUserWhenUserExists() {

        // Arrange
        User user = new User(1L, "Nish");

        when(userRepository.findById(1L))
            .thenReturn(Optional.of(user));

        // Act
        User result = userService.getUserById(1L);

        // Assert
        assertNotNull(result);
        assertEquals("Nish", result.getName());

        verify(userRepository).findById(1L); // Verifies a method invocation
    }
}
```

Internally, Mockito uses a combination of method interception, invocation recording, 
and stubbing to achieve this.

### Component Testing

Test an individual component of an application along with its **internal dependencies** to 
verify that the component behaves correctly as a whole.

The key idea is that we test a complete functional component rather than an individual 
method.

```java
@SpringBootTest
@AutoConfigureMockMvc
class UserComponentTest {

    @Autowired
    private MockMvc mockMvc; // Simulates HTTP requests without starting an actual HTTP server.

    @Autowired
    private UserRepository userRepository;

    @BeforeEach
    void setUp() {
        userRepository.deleteAll();

        userRepository.save(
            new User(1L, "Nish")
        );
    }

    @Test
    void shouldReturnUserById() throws Exception {

        mockMvc.perform(
                get("/users/1")
            )
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name")
                .value("Nish"));
    }
}
```

<Note>
Component testing is especially important in backend systems because individual classes 
might work correctly in isolation, but multiple classes working together can still 
introduce defects.

The important distinction is that component testing generally uses real internal 
dependencies, although external dependencies can still be mocked or simulated.
</Note>

### Black Box Testing

Black box testing is a software testing technique in which we validate an application's 
functionality without knowing or depending on its internal implementation.

As black box testers, we don't need to know:

- Which controller handles the request.
- Which service executes the business logic.
- Which database is queried.
- Whether the application uses JPA or JDBC.

We only care whether the API returns the expected response.

### How to implement black box tests?

REST Assured is a Java library that allows us to test REST APIs by sending HTTP requests 
and validating HTTP responses.

The important idea is that we interact with our application through its public API, 
without depending on its internal implementation.

REST Assured follows a simple request-response validation model. The three main stages are:

1. `given()`: Define request configuration
2. `when()`: Execute HTTP request
3. `then()`: Validate response

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class UserApiTest {

    @LocalServerPort
    private int port;

    @BeforeEach
    void setUp() {
        RestAssured.port = port;
    }

    @Test
    void shouldReturnUserDetails() {

        given()
            .basePath("/api/users/101")
        .when()
            .get()
        .then()
            .statusCode(200)
            .contentType(ContentType.JSON)
            .body("id", equalTo(101))
            .body("name", equalTo("Nish"))
            .body("email", equalTo("nish@example.com"))
            .body("status", equalTo("ACTIVE"));
    }
}
```

### System Testing 

System testing verifies whether an entire application works correctly as a complete 
system against its functional and non-functional requirements.

The objective is to validate the entire system, not just individual services.

The only thing that is faked is a set of downstream systems the app depends on.

#### How to implement system tests in distributed environments?

TestNG (Test Next Generation) is a Java testing framework inspired by JUnit and NUnit.
It is particularly useful for organizing large automated test suites, including API-level 
system tests.

#### What is a WireMock server?

A lightweight fake HTTP server. You give it mappings, rules like "if someone posts to a URL, reply to those with this JSON," and 
it pretends to be any downstream you point the app at.

### Extra 

#### Why do we need blackbox testing?

1. **To validate business requirements**: For example, when a customer initiates a payment of AUD 1,000, the 
API should accept the valid request and return the expected payment details.

2. **To verify error handling**: If the customer has insufficient funds, the payment should be rejected 
according to the API contract, and no unauthorized debit should occur.

3. **To protect financial integrity**: We need to ensure that payments aren't duplicated, funds aren't 
incorrectly debited, and failed payments are handled correctly.

4. **To validate API contracts**: The API should return the correct HTTP status codes, response fields, error 
messages, and data formats expected by its consumers.

5. **To test integration behavior**: Outbound payments often depend on downstream banks, payment gateways, 
and other services. Black-box tests help verify how the API behaves when those dependencies succeed, fail, or 
time out.

6. **To prevent regressions**: When developers change the payment service, existing black-box tests help 
confirm that previously working functionality still behaves as expected.

### How to write blackbox tests?

Blackbox tests usually follow the **Given-When-Then** naming convention used in unit and integration testing. For example:
`givenValidPayment_whenPostPayment_thenSuccess()`.

- **Given ValidPayment**: A valid payment request exists, with valid account details, a positive amount, 
and a supported currency.

- **When PostPayment**: The client submits the payment using the `POST /api/v1/payments` endpoint.

- **Then Success** — The API returns the expected success status, payment ID, and payment status.

#### What is WireMock?

WireMock is a tool used to mock HTTP APIs so that you can test your application without depending on real 
external services.

For example, in an outbound payment system, you can use `WireMock` to simulate the responses of a 
downstream bank or payment gateway.

Wiremock's Admin API allows you to configure and control a `Wiremock` server programmatically, including 
creating, viewing, and deleting stubs.

##### How to create a stub using WireMock?

```json
POST /_admin/mappings
```

This is the WireMock's admin endpoint for creating stubs. You send a configuration to `Wiremock` 
describing which request to match and what response to return.

```java
ObjectNode mapping = JSON_MAPPER.createObjectNode();    // {}

ObjectNode request = mapping.putObject("request");      // { "request": {} }
request.put("method", "POST");                          // { "request": { "method": "POST" } }
request.put("url", url);                                // { "request": { "method": "POST", "url": url } }

ObjectNode response = mapping.putObject("response");
response.put("status", status);
response.putObject("headers").put("Content-Type", contentType);
response.put("body", body);

HttpRequest requestToWireMock = HttpRequest.newBuilder()
    .uri(URI.create("http://localhost:" + port + "/__admin/mappings"))
    .timeout(Duration.ofSeconds(5))
    .header("Content-Type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString(JSON_MAPPER.writeValueAsString(mapping)))
    .build();

HttpResponse<String> responseFromWireMock HttpClient.newHttpClient()
    .send(requestToWireMock, HttpResponse.BodyHandlers.ofString());
```

### Performance Testing

A performance test asks:

```
Can we process 10,000 orders/sec while keeping p99 latency below 500 ms?
```

For example, you might define an SLA/SLO:

```
Throughput:       10,000 requests/sec
p50 latency:      < 100 ms
p95 latency:      < 300 ms
p99 latency:      < 500 ms
Error rate:       < 0.1%
CPU utilization:  < 80%
```

These become the performance requirements you're testing against.

---

### Acceptance Testing

Acceptance testing verifies that the software satisfies the business requirements and expectations of the 
customer/user and is ready to be accepted or released.

---

### Regression Testing

Regression testing means testing existing functionality again after a code change to make sure the change 
hasn't broken something that previously worked.
