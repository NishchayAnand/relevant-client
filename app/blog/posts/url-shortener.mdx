A URL shortening service allows us to create a short, easy-to-remember URL for a long URL.

![url-shortener](/url-shortener/url-shortener.png)

---

### Functional Requirements

1. Users should able to submit a long URL along with additional details like custom alias, expiration date, etc., 
and get a shortened version.

2. When a user visits the shortened URL, they are redirected to the original URL.

---

### Non-Functional Requirements

1. The system should scale to support `1 Billion` shortened URLs and `100 Million` visits per day.

2. Each shortened URL should be unique.

3. The redirection should occur with minimal latency (`< 100ms`).

---

### Design Rationale

#### **<span className="text-emerald-800">Q1. How to generate a unique shortened URL?</span>**

We need some entropy (randomness) to try to ensure that our codes are unique. Considering we are dealing 
with ?? write request per day, a random number generator does not provide enough entropy to ensure that our 
codes are unique.

We could use a hash function like `SHA-256` to generate a fixed-size hash code. Hash functions take an input 
and return a deterministic, fixed-size string of characters. Hash functions also provide a high degree of 
entropy, meaning that the output appears random and is unlikely to collide for different inputs.

<Note>
Pure hash functions are deterministic: the same long URL always maps to the same short code without needing 
to query the database. This may be desirable (deduplication) or not (if you need multiple codes per URL or 
want to prevent guessability/adversarial preimages). For the latter cases, add a secret salt or nonce (HMAC). 
</Note>

We can then take the output and encode it using a base62 encoding scheme and take just the first N characters 
as our short code. N is determined based on the number of characters needed to minimize collisions 
(e.g., 8 characters gives 62^8 ≈ 218 trillion possible codes).

<Note>
Why base62? 

It's a compact representation of numbers that uses 62 characters (a-z, A-Z, 0-9). The reason it's 62 and not 
the more common base64 is because we exclude `+` and `/`. The slash is a path separator in URLs and the plus 
sign can be interpreted as a space in query strings.
</Note>

To reduce collision probability, we need higher entropy, which means generating longer short codes. However, 
longer codes negate the benefit of having a short URL. Detecting and resolving collisions also adds database 
lookups on insertion, introducing latency and complexity.

### Sequence Flow

#### Use Case 1: Create Short URL

1. `User` submits a **long URL** along with additional details like **custom alias**, **expiration date**, etc. 

2. The `Client (browser or mobile app)` sends a `POST /shorten` request (along with the long URL and additional 
details) to the `Shortening Service`.

3. The `Shortening Service` validates the request (`what validations?`) and creates a unique shortened URL.

4. Once the shortened URL is created, the `Shortening Service` inserts a record into the database (`what 
should be the name of the table?`) to store the mapping between the long URL and the shortened URL.

5. Finally, the `Shortening Service` returns the shortened URL to the `Client` with HTTP status code 
`201 Created`.

#### Use Case 2: Redirect to Original URL

1. The `Client (browser or mobile app)` sends a `GET /<shortened-url>` request to the `Redirection Service`.

2. The `Redirection Service` looks up the shortened URL in the database.

3. If the shortened URL is found and is not expired, the `Redirection Service` sends an HTTP redirect response 
to the `Client` with the original URL in the `Location` header (`Why in the Location header?`, `What HTTP 
status code to return?`).
